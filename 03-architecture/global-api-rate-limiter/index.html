Global API Rate Limiter 設計

設計入口與需求邊界

先分清三件事：需求問題用來確認必要的限制與行為；設計假設是在資訊不足時明示暫定前提；設計選擇才是依需求決定 key、演算法、儲存與跨區協調。不要直接假設以 IP 限流，也不要先挑演算法。

需求問答有三個並列面向，不是執行步驟：限流契約：限制誰，超限怎麼辦？、流量語意：允許 burst，還是嚴格時間窗？、全域語意：跨區共享多少額度，規則多久生效？。

責任邊界：DNS、Global Load Balancer 或 routing layer 決定 client 前往哪個 region；Rate Limiter 依規則判定請求是否可進入，保護可用性、公平性與下游容量。

推薦路徑（由左往右）：先釐清需求 → 選型卡與其下的演算法區（五種演算法是並列選項，不是執行步驟）→ Token Bucket 單區實作 → 其下的邏輯架構把系統分成資料面與控制面：資料面往右看多維度 Key 與熱點，控制面往下看全域協調、Quota Lease、完整判定路徑與失敗處理。其他四種演算法的實作是 Token Bucket 實作右側的平行分支，用來比較判定路徑差異。容量估算往下延伸到攻擊防禦區（分層防禦、Edge／WAF、Login／OTP 濫用型限流）。

限流契約：限制誰，超限怎麼辦？

要確認的事：限流的對象，以及用完額度後對 client 的承諾。

主要限流身分是什麼？

What is the primary rate-limit identity?

Should we limit by API key, tenant, user, IP address, endpoint, or a combination?

影響的決策：counter key、租戶公平性與資料分區方式。外部 API 平台通常優先考慮 API key 或 tenant；多個使用者可能共用 NAT IP，只以 IP 限流可能誤傷合法流量。

超限後怎麼處理？

What should happen when a client exceeds the limit?

Should we reject immediately with HTTP 429 and a Retry-After header, queue requests, or degrade service?

影響的決策：client retry behavior、下游負載、API contract 與可觀測性。

流量語意：允許 burst，還是嚴格時間窗？

要確認的事：短暫尖峰是否可接受，以及限制要精確到什麼程度。這兩項需求是演算法選擇的依據，不是先選演算法再補理由。

Should clients be allowed to send short bursts, as long as their average request rate stays within the plan limit?

影響的決策：是否需要允許短暫 burst，以及是否適合採用 Token Bucket。

Do we need an exact limit over a rolling time window, or is approximate enforcement acceptable?

影響的決策：限流精確度、儲存與計算成本，以及請求延遲。例如「任何連續 60 秒不得超過 1,000 次」比「每分鐘大致不超過 1,000 次」更嚴格。

全域語意：跨區共享多少額度，規則多久生效？

要確認的事：限額的跨區範圍，以及設定更新容許多長的傳播時間。

Do we need global limits across all regions, per-region limits, or both?

影響的決策：region 是否必須共享計數器、跨 region 延遲，以及可接受的一致性誤差。要明確詢問是否容許短暫超限或跨區協調延遲。

How quickly must rule changes take effect?

影響的決策：config propagation、cache 策略，以及是否容許短時間使用舊規則。跨區額度判定不等於導流，見 設計入口與需求邊界。

容量估算與 Hot Path 狀態

先分清 hot path 狀態與 request log：每次判定只需要 bucket state（剩餘 token、lastRefill）。IP、device、browser 等 request metadata 屬於稽核或分析 log，非同步寫入 ELK、ClickHouse 或 object storage，不進入判定路徑。

狀態量以 active key 估算：每個 key 的欄位約 32 bytes，加上 Redis 每個 key 約 50–100 bytes 的額外開銷；100 萬個 active key 約 100MB 級，單一 Redis node 就能容納。TTL 約為 capacity ÷ refillRate，讓閒置 key 自動回收。

吞吐與延遲預算決定 Redis 規模：Redis ops/s ≈ 峰值 QPS × 每個 request 檢查的維度數，例如 10k QPS × 4 個維度（API、商戶、domain、region，見 多維度 Key：先依基數分類）= 40k ops/s。limiter 加在每個 request 上，判定預算通常只有個位數 ms，所以 Redis 呼叫要設短 timeout，並且就近部署。

五種演算法，三種語意：先依需求選語意，再依精準度與 state 成本選實作。

Token Bucket：允許有限的短暫 burst

核心想法：bucket 內有 token，token 依固定速率補充。每個 request 消耗一個 token；有 token 就通過，沒有就拒絕或等待。bucket 的容量限制最多可累積多少未使用額度。

  • 例：capacity = 10，refill rate = 10 requests/minute。滿 bucket 的 client 可以在瞬間送出 10 個 request，但之後必須等待 token 逐步補回。
  • 它限制的是長期平均速率，同時容許有上限的短暫尖峰。

實際應用：

  • Public API gateway，讓合法 client 在短暫 burst 時不會立刻失敗。
  • 依 API key、tenant、user 或 endpoint 執行不同方案的 quotas。
  • Login、password reset 等 endpoint 的 abuse protection，允許少量正常重試但阻擋持續攻擊。

實作：Token Bucket：Redis State 與 Refill 判定。

Use Token Bucket when we need to enforce a long-term average rate while allowing bounded short bursts.

Leaky Bucket：以固定節奏保護下游

核心想法：請求先進入一個有限 queue，再以近似固定速率流向下游。輸出速率比瞬間輸入速率更重要；queue 滿時，新請求必須被拒絕、丟棄，或採取其他明確策略。

  • 例：client 在同一秒送來 10 個工作，但 worker 每 6 秒只取出 1 個。下游看到的是穩定流量，不是瞬間的尖峰。
  • 它本質上是 traffic shaping，不只決定 request 能否進入，也控制工作送往下游的節奏。

實際應用：

  • 保護吞吐固定或成本昂貴的下游，例如 payment processor、email provider、第三方 API。
  • 非同步 job pipeline，將突然增加的工作平滑地交給 worker。
  • 寫入資料庫、發送通知或執行批次任務前的節流。

限制與提醒：

  • 同步 API 不宜長時間排隊，否則 client 可能 timeout，服務也會累積連線與記憶體壓力。
  • 常見做法是 gateway 先用 Token Bucket admission control，再對非同步工作使用 queue-based shaping。

實作：Leaky Bucket 實作：真的排隊（Queue 版）或只用時間計算（Meter 版）。

Use a Leaky Bucket or queue-based shaper when the downstream system needs a predictable, smoothed request rate.

比較｜Token Bucket 與 Leaky Bucket：裝額度還是裝請求

兩者都叫 bucket，但桶裡裝的東西不同：一個裝額度，一個裝請求。

比較 Token Bucket Leaky Bucket
控制什麼 准入速率（admission control） 送往下游的速率（traffic shaping）
桶裡裝什麼 未使用的額度 token 等待處理的 request
遇到 burst 有 token 就立即放行，最多 B 個 先進 queue，再以固定速率送出
超限時 立即拒絕，回 429 queue 未滿就排隊；滿了才拒絕或丟棄
對延遲的影響 不增加延遲 增加排隊延遲
參數 補充速率 r、容量 B 流出速率、queue 長度
下游看到的流量 仍可能有尖峰（最多 B） 平穩

一句話記：Token Bucket 決定「能不能進」，Leaky Bucket 決定「多快送出」。

Fixed Window Counter：最簡單，但交界處會放大流量

核心想法：把時間切成固定窗口（例如每分鐘），每個 client 每個窗口一個計數器；request 進來就加一，超過上限就拒絕，窗口結束後歸零。

  • 每個 key 只有一個整數，state 最小。實作見 Fixed Window Counter 實作：INCR 與 EXPIRE。
  • 邊界問題：上限 10 次／分鐘時，client 在 00:59 與 01:00 各送 10 次，兩批分屬不同窗口而全部放行，短短 2 秒內通過 20 次，約為上限的 2 倍。想保留小 state 又避開這個問題，改用 Sliding Window Counter：用兩個固定窗口近似滑動窗口。

實際應用：

  • 以自然日或自然月計算的帳單 quota。
  • 內部服務、可容忍邊界誤差的低風險 endpoint。

Use Fixed Window Counter when simplicity and minimal state matter more than precision at window boundaries.

Sliding Window Counter：用兩個固定窗口近似滑動窗口

核心想法：只保存目前與前一個固定窗口的計數，再把前一窗口仍落在滑動窗口內的部分按比例加權：

estimated=currentCount+previousCount×previousWindowOverlapRatio\text{estimated} = \text{currentCount} + \text{previousCount} \times \text{previousWindowOverlapRatio}estimated=currentCount+previousCount×previousWindowOverlapRatio

重疊比例 = 1 − 目前窗口已經過的比例。

  • 例：上限 10 次／分鐘，前一分鐘 8 次，目前這分鐘已過 25%、已有 3 次；估計值 = 3 + 8 × 0.75 = 9，仍可放行。

跟 Fixed Window Counter 的差別：兩者的 state 幾乎相同（Fixed 存 1 個計數，Counter 存 2 個），差別在判斷時有沒有看前一窗口。Fixed 一進新窗口就從 0 開始；Counter 讓前一窗口的計數隨時間逐步釋放。

延伸：邊界情境：三種時間窗在 01:00 與 01:30 怎麼判、Sliding Window Counter：誤差從哪裡來。

實作：Sliding Window Counter 實作：兩個窗口 Key 加權。

實際應用：

  • 高 QPS、大量 key 的一般 public API，想要滑動窗口的行為，但不想為每個 key 保存每筆 timestamp。
  • CDN／edge 層的 per-IP rate rule，key 數量極大，只能負擔固定大小的 state。

Use Sliding Window Counter when we want rolling-window behavior at fixed-window cost and can accept a small estimation error.

Sliding Window Counter：誤差從哪裡來

公式假設前一窗口的請求平均分布。

前一窗口的實際分布 估計值相對真實值 結果
集中在窗口尾端（例如全在 00:59） 偏低 多放行；01:30 時真實滾動計數仍是 10，估計只有 5
集中在窗口開頭（例如全在 00:01） 偏高 誤拒；01:00 時真實滾動計數已是 0，估計值仍是 10
大致平均 接近 誤差小

一般流量下誤差很小，但 client 刻意集中送出時仍可能短暫超限，所以必須精確的計數改用 Sliding Window Log。

Sliding Window Log：精準記錄最近一段連續時間的每筆請求

核心想法：規則是「任何連續 60 秒最多 10 次」時，每次請求都往回數前 60 秒實際放行了幾筆，而不是只看目前落在哪一個固定分鐘。為了數得精準，每筆放行的 request 都記下 timestamp。

  • 邊界例子：client 在 00:59 發 10 次，在 01:00 再發 10 次。Fixed Window 把兩批分屬不同分鐘而放行 20 次；Sliding Window Log 看見前一批的 10 筆 timestamp 仍在最近 60 秒內，拒絕第二批，直到 01:59 那批過期。
  • 它的價值是避免 client 利用固定時間窗邊界製造雙倍 burst，而且沒有估算誤差。

實作：Redis Sorted Set 保存 timestamp，見 Sliding Window Log 實作：Sorted Set 判定路徑與 Retry-After。

代價：每個 key 最多保存「上限」筆紀錄。上限 10 次／分鐘時很便宜；上限 10,000 次／分鐘又有大量 key 時，記憶體與每次清理的成本都高，這時改用 Sliding Window Counter：用兩個固定窗口近似滑動窗口。

實際應用：

  • 上限小、必須精確的計數，例如登入失敗次數、OTP 驗證次數。
  • 合約或 plan 明確承諾「任何連續 60 秒」的用量上限。
  • 對單一 endpoint 需要精確控制短期呼叫量的情況。

Use Sliding Window Log when the limit is small and must be exact over any rolling interval; it stores one timestamp per allowed request, so memory grows with the limit.

Token Bucket：Redis State 與 Refill 判定

1. Bucket state 只保存可變計數

每個 API key + endpoint group 保存剩餘 token 與 lastRefillMs。capacity、refill rate 與 request cost 從設定服務或快取取得，而不在每筆 bucket state 重複保存。

2. 每次請求先 refill，再判定與扣除

refilled=min⁡(capacity,oldTokens+elapsedMs×refillRate/1000)\text{refilled} = \min(\text{capacity}, \text{oldTokens} + \text{elapsedMs} \times \text{refillRate} / 1000)refilled=min(capacity,oldTokens+elapsedMs×refillRate/1000)

若 refilled >= requestCost，扣除 cost 並放行；否則拒絕。bucket 不存在時可視為滿 bucket，因為該 client 已長時間沒有使用額度。

延伸：Token Bucket：Lua Script 原子判定與回傳、Token Bucket：TTL 回收閒置 Key。

Token Bucket：Lua Script 原子判定與回傳

1. 為什麼要 Lua script

如果 gateway 用 GET → application calculation → SET，兩個並發 request 可能都讀到最後一個 token，並同時放行。

將「讀 state、refill、判定、扣 token、設定 TTL、回傳結果」包成單一 Redis Lua script，可以避免同一 Redis instance 上的 race condition。建議在 script 使用 Redis server time，降低 gateway clock skew 的不公平。

2. 回傳與 client contract

  • allowed
  • remainingTokens
  • retryAfterMs
  • limit
  • resetAt 或等價時間

Gateway 在拒絕時回 HTTP 429，並加入 Retry-After、remaining quota 與 reset time 等 headers。

Token Bucket：TTL 回收閒置 Key

TTL 可約為 bucket 從空補滿所需時間，加上 buffer：

TTL≈capacityrefillRate\text{TTL} \approx \frac{\text{capacity}}{\text{refillRate}}TTL≈refillRatecapacity​

這避免大量不活躍 API key 長期占用 Redis 記憶體。Key 過期後再出現時視為滿 bucket，結果與一直保存相同。

邏輯架構：資料面與控制面分開

                 ┌──────────── 控制面（全域，不在請求路徑上）────────────┐
                 │  Rule Service      規則與版本（限制誰、多少、成本）   │
                 │  Quota Allocator   依各區需求發 regional lease       │
                 │  Usage Aggregator  收各區用量，算全域超放量           │
                 └──────▲ 回報用量 / ▼ 推送規則與 lease ──────────────────┘
                        │
 Client → DNS/GLB → Region A ─────────────────────────────────────────────
                    Edge/WAF → API Gateway ──────────────→ 業務服務
                               └ Limiter 模組
                                  ├ 規則快取（本地）
                                  ├ 本地計數 / 預取的 token
                                  └→ Regional Redis Cluster（bucket state）

判定請求的路徑只在本區完成，同步的跨區呼叫一律不放在這條路徑上。

  • 資料面（gateway 裡的 limiter 加上本區 Redis）：個位數 ms 內判定允許或拒絕。
  • 控制面（Rule Service、Quota Allocator、Usage Aggregator）：規則、跨區額度分配與全域用量；非同步運作，掛掉時資料面沿用最後拿到的規則與 lease。
問題 落在哪一面 段落
本區的 key 怎麼切、單一 shard 怎麼不被打爆 資料面 多維度 Key：先依基數分類、熱點 Key：判斷來源，依誤差方向選解法
全域額度怎麼分到各區 控制面 Global Rate Limiter：事前分配還是事後對帳、Global Rate Limiter：Quota Lease 的分配、到期與故障

兩面串起來的流程見 一個請求的完整判定路徑。

Keep the decision path inside the region: the data plane decides in milliseconds with local rules and leases, and the control plane distributes rules and quota asynchronously, so a control-plane outage degrades accuracy, not availability.

高基數、專屬於某個身分 API key、user、商戶 多 低 記憶體與 TTL 回收
低基數、大家共用 region、domain、整個 endpoint 少 極高 天生就是熱點
組合維度 商戶 × API 多 中 規則數量膨脹

3. 分類決定 key 放在哪裡

一個 Lua script 只能操作同一個 Redis Cluster slot 的 key。

  • 身分維度：用 hash tag {merchant:m42} 讓同一商戶的各維度落在同一個 slot，在一個 Lua 裡先檢查所有 bucket、再一起扣除，避免某個維度已扣、另一個維度卻拒絕。
  • 共用維度：不能和身分 key 放在同一個 slot，否則所有商戶的請求都擠到同一個 shard。改走本地近似計數或 lease。

身分維度保護公平，要精確；共用維度保護總容量，近似即可。

延伸：多維度 Key：跨 slot 無法原子時的取捨、熱點 Key：判斷來源，依誤差方向選解法。

多維度 Key：跨 slot 無法原子時的取捨

規則命中的 key 分散在不同 Redis Cluster slot 時，無法用一個 Lua script 原子完成「全部檢查再一起扣」。

做法 怎麼做 代價
依序扣除，被拒時退還 先扣 A，B 拒絕時把 A 加回去 中間狀態短暫不一致，別的請求可能因此誤被拒

建議答法：身分維度放同一個 slot、用 Lua 原子判定；共用維度在本地近似處理。兩者精確度不同，因為保護的東西不同：身分維度保護公平，共用維度保護總容量。

Identity dimensions share a hash-tagged slot and are checked atomically in one Lua script; shared dimensions like region are enforced approximately in local memory, because they protect total capacity rather than fairness.

熱點 Key：判斷來源，依誤差方向選解法

1. 什麼時候算熱點

單一 Redis shard 約可處理 10 萬 ops/s；單一 key 的 QPS 接近 shard 容量的一成時就要處理。熱點有兩種來源：

  • 結構性熱點：低基數的共用維度，例如 region、domain，一定會熱。

  • 偏斜熱點：某個大商戶的流量是其他商戶的上千倍。

2. 三種解法，差在誤差往哪邊偏

解法 機制 Redis 負載 誤差方向 適合
Local token lease（預取） gateway 一次向 Redis 拿 n 個 token，在本地扣，用完再拿 降為約 1/n 少放：token 卡在閒置的 gateway；lease 要設到期並歸還 大商戶這類偏斜熱點
拆成 N 個子 bucket key:0..N-1，各分 limit/N，請求隨機打到其中一個 分散到 N 個 shard 提早拒絕：流量不均時某個子 bucket 先用完 要較精確、但單一 key 扛不住
本地計數加定期同步 每台 gateway 自己計數，每 Δt 同步一次總數 幾乎為 0 多放：上限約為速率 × Δt 共用維度，只需保護總量

一句話記：預取 lease 少放，本地同步多放，拆分提早拒絕。 選哪一種，看這個維度能容忍哪一種錯。

3. 試算：預取 lease

商戶 m42 上限 50k/s，20 台 gateway。不處理時 50k ops/s 全部打在同一個 shard。每次預取 100 個 token，Redis 約降到 500 ops/s；最壞 20 × 100 = 2,000 個 token 卡在閒置的 gateway，約占每秒額度 4%，表現為少放。

For a hot key I choose by error direction: prefetched leases under-admit, local counting with periodic sync over-admits, and splitting into sub-buckets rejects early when traffic is uneven.

實作路徑的三個分歧

  1. 同步判定還是排隊：只有 Leaky Bucket 的 queue 版會改變 API 回應語意（202 加非同步結果）；其餘四種都是同步 allow／deny，超限回 429。
  2. 被拒絕的請求算不算：Fixed Window 的 INCR-first 寫法會把拒絕也算進去；其他都在 Lua 內先判定、通過才寫入。
  3. 能不能跨 region：計數型（Fixed、Sliding Counter）可以非同步加總；Token Bucket 用 quota lease；Sliding Log 需要每筆 timestamp，通常只做單區。

Leaky Bucket 實作：真的排隊（Queue 版）或只用時間計算（Meter 版）

兩者差在 client 當下能不能拿到結果：Queue 版先收下、晚點給結果；Meter 版當場決定放行或拒絕。

  • Queue 版（traffic shaping）：request 或 job 寫入有界 queue（Redis List、RabbitMQ、Kafka、SQS），consumer 以固定速率取出送往下游。API 先回 202 Accepted 加 job id，結果非同步取得。
  • Meter 版（GCRA）：不真的排隊，每個 key 只存一個 TAT（theoretical arrival time），判斷「如果以固定速率流出，這個 request 還放不放得進桶」。行為等同 Token Bucket，可用在同步 API，例如 redis-cell 的 CL.THROTTLE。「Meter」來自經典分類 leaky bucket as a meter（相對於 as a queue），GCRA 是 ATM 網路標準化的寫法；它跟 Token Bucket 數學上等價，差在 state 只存一個時間點，不用另外算 refill。

延伸：Leaky Bucket 實作：Queue 版的判定路徑與差異。

Leaky Bucket 實作：Queue 版的判定路徑與差異

1. 判定路徑

  1. 入列前檢查長度：在同一個 Lua script 內 LLEN 與 RPUSH，長度已達容量就拒絕；用 MQ 時改設 queue 上限，例如 RabbitMQ x-max-length 加 overflow: reject-publish。
  2. Consumer 控制流出速率：單一 consumer 固定間隔取出；多個 consumer 時每個分 1/N 速率，或共用一個中央 limiter。
  3. 下游失敗時 retry 加 backoff，多次失敗進 DLQ。

2. 跟 Token Bucket 實作的差異

Token Bucket 只記帳、當場判定，request 本身不留下；Queue 版把 request 本身留下來排隊。下面四點差異都從這裡來。

面向 Token Bucket Queue 版
State 固定兩個數字（tokens、lastRefillMs），不隨流量變大 queue 本身，每個等待的 request 一個 entry，記憶體隨排隊數成長
Client 當下拿到 結果：200 或 429 已受理：202 加 job id，結果要查詢狀態或等 callback
Retry-After (cost − tokens) ÷ refill rate queue 長度 ÷ 流出速率，例如排 30 個、每秒處理 5 個 ≈ 6 秒
觀測重點 allow／reject rate queue depth、等待時間、DLQ 數量

比喻：Token Bucket 像門口發號碼牌，牌發完就請你下次再來，店裡只記剩幾張；Queue 版像讓你進來排隊並給取餐號碼，店裡要記每個在等的人，你也要等叫號才拿到餐。

Fixed Window Counter 實作：INCR 與 EXPIRE

1. State 是一個整數

Key 帶窗口編號，例如 rl:{tenant:t7}:202610281405，窗口編號 = floor(now ÷ 窗口長度)。Value 是本窗口已放行的次數。

2. 判定路徑

  1. INCR key
  2. 回傳值是 1（本窗口第一筆）時 EXPIRE key 窗口長度
  3. 回傳值 > 上限就拒絕

INCR 本身是原子的，但 INCR 與 EXPIRE 是兩個指令，中間失敗會留下沒有 TTL 的 key。把兩步包進 Lua script，或先 SET key 0 EX ttl NX 再 INCR。

先加再比較的寫法會把被拒絕的 request 也算進去。Fixed Window 本來就粗略，通常可接受；要精確時改成 Lua 先判定、未超限才加。

3. Retry-After

Retry-After = 窗口結束時間 − now。所有 client 在同一個整點重置，會同時重試，client 端要加 jitter。

4. 跨 region

計數只是整數，各 region 可以各自計數、非同步加總，或各自分配 1/N 額度。這是時間窗計數中最容易跨區的一種。

Sliding Window Counter 實作：兩個窗口 Key 加權

1. State 是兩個整數

與 Fixed Window 相同的 key 格式，只是判定時同時讀目前與前一窗口：rl:{tenant:t7}:<目前窗口>、rl:{tenant:t7}:<前一窗口>。TTL 設為 2 個窗口長度，讓前一窗口在需要時仍讀得到。

2. 判定路徑（單一 Lua script）

  1. GET 前一窗口計數 prev、目前窗口計數 curr
  2. 重疊比例 = 1 − 目前窗口已經過的時間 ÷ 窗口長度
  3. estimated = curr + prev × 重疊比例
  4. estimated + cost ≤ 上限才 INCR 目前窗口並設 TTL，否則拒絕

必須先判定再寫入，所以一定要用 Lua；不能像 Fixed Window 直接 INCR 再比較，否則被拒絕的 request 也會推高計數。

3. Retry-After

前一窗口的權重隨時間線性下降，可以解出何時 estimated 降到上限以下：

elapsed≥W×(1−limit−cost−currprev)\text{elapsed} \ge W \times \left(1 - \frac{\text{limit} - \text{cost} - \text{curr}}{\text{prev}}\right)elapsed≥W×(1−prevlimit−cost−curr​)

curr 本身已達上限時，要等到下一個窗口。實務上也可以保守地回到窗口結束時間。

4. 跟 Fixed Window 實作的差異

多一次讀取與一次浮點計算，換來沒有 2 倍邊界問題。記憶體同級，跨 region 也同樣可以非同步加總兩個計數。

Sliding Window Log 實作：Sorted Set 判定路徑與 Retry-After

1. State 是窗內每筆放行紀錄

Redis Sorted Set：score 是 timestamp，member 必須唯一。同一毫秒可能有多筆 request，所以 member 用 timestamp 加 request id 或隨機後綴，不能只用 timestamp。

2. 判定路徑（單一 Lua script）

  1. ZREMRANGEBYSCORE key 0 (now − 窗口長度) 移除窗外紀錄
  2. ZCARD key 計數
  3. 未超限才 ZADD key now member，並 PEXPIRE key 窗口長度

被拒絕的 request 不寫入，否則持續重試的 client 會一直卡在窗內。在 script 內用 Redis server time，避免 gateway clock skew。

3. Retry-After

ZRANGE key 0 0 WITHSCORES 取最舊一筆：Retry-After = 最舊 timestamp + 窗口長度 − now。這是五種演算法中唯一能精確算出何時有額度的。

延伸：Sliding Window Log 實作：記憶體成本與跨 region 限制。

Sliding Window Log 實作：記憶體成本與跨 region 限制

1. 成本決定適用範圍

每個 key 最多保存「上限」筆，每筆加上 Sorted Set 的額外開銷約數十到上百 bytes。上限 1,000 次、100 萬個 key 就是數十 GB 級，所以只適合上限小的規則。ZREMRANGEBYSCORE 與 ZADD 是 O(log n)，也比計數型慢。

2. 跨 region

需要每筆 timestamp 才精確，無法像計數那樣非同步加總。通常只做單區，或對低 QPS、高價值的操作走中央強一致儲存。

Global Rate Limiter：事前分配還是事後對帳

1. 問題本質

同一個 tenant 的流量同時進到多個 region，全域上限是 L。要讓各區加總不超過 L，又不能讓每個請求同步跨區。

Per-region 與 global limit 是不同語意：各 region 使用本地 Redis 延遲最低、故障隔離最好，但同一 client 跨區請求會放大全域額度。先決定可接受多少 over-admission、跨區延遲與單點風險。

2. 四種做法，背後是兩個家族

做法 家族 機制 延遲 誤差 適合
各區獨立 — 每區上限 L/N，或各給 L 最低 L/N：流量集中在一區時少放；各給 L：最多放到 N 倍 可容忍誤差的一般 API
Quota lease 事前分配 控制面依近期需求把 L 切給各區，每 Δt 重新平衡 本區內完成 總和不超過 L，不會多放；需求轉移時少放 主流折衷
非同步對帳 事後對帳 各區本地計數，非同步交換用量（類似 G-Counter） 本區內完成 多放，上限約為全域速率 × 同步延遲 計數型演算法、可接受短暫超限
強一致中央計數器 — 每個請求都跨區查詢 加 50–150ms，且是單點 精確 低 QPS、高價值、絕不能超限

核心論點：事前分配寧可少放，事後對帳寧可多放。先問這個 endpoint 怕哪一種錯，再選家族。

3. 熱路徑保持本地，誤差必須可量化

一般 API 平台採 regional Token Bucket 加中央分配的 quota lease。資料面維持低延遲；控制面管理公平性、quota 補貨與 rule propagation，並讓全域超放量與 lease 使用率可觀測。

Pre-allocation errs toward rejecting; post-hoc reconciliation errs toward over-admitting. I pick the family by asking which mistake the endpoint can afford.

Global Rate Limiter：Quota Lease 的分配、到期與故障

1. 怎麼分

控制面依前一週期各區實際用量的比例分配全域上限 L，另外保留約 10% 當全域備用池，突發的區可以申請。

  • 例：L = 10k/min，三區用量 60%／30%／10%。先保留 1k，其餘 9k 分成 5.4k／2.7k／0.9k。

  • 每 Δt（例如 10 秒）依最新用量重新平衡。

2. Lease 一定要有到期時間

某一區網路斷開時，lease 到期就自動失效，那一區不能無限期用舊額度；其他區在下次平衡時接手這份額度。沒有到期時間，斷線的區持續放行，加上其他區新拿到的額度，總和就超過 L。

3. 故障時的退路

  • 控制面掛掉：各區沿用現有 lease 到期，之後退回保守的靜態值，例如 L/N × 0.8。

  • Region 掛掉：GLB 把流量導到其他區；那些區需求上升，下次平衡時拿到更多額度。

  • 流量整批轉移：例如全部移到亞洲區。重新平衡前的過渡期，亞洲區額度不足而少放；備用池與縮短 Δt 可以降低影響。

4. 觀測

全域超放量（全域實際放行 − L）、各區 lease 使用率、平衡延遲、備用池水位。

Each region enforces a lease from the control plane locally; leases expire so a partitioned region cannot keep spending quota, and when the control plane is down regions fall back to a conservative static share.

一個請求的完整判定路徑

  1. Gateway 用本地規則快取，比對出這個請求命中的維度。

  2. 共用維度（region、domain）：用本地計數或 lease 判斷，不夠就拒絕，不碰 Redis。

  3. 身分維度（商戶、商戶 × API）：本區 Redis 的一個 Lua script（同一個 slot），全部通過才扣；大商戶改用預取的 token 在本地扣。

  4. 放行後非同步回報用量給 Usage Aggregator；拒絕時回 429 加 Retry-After。

  5. 控制面每 Δt 彙整各區用量、重新分配 lease，推送給各區。

  6. 觀測全域超放量、lease 使用率、平衡延遲與熱點 key 的 QPS。

先查便宜的本地維度，攻擊流量在碰到 Redis 之前就能被擋下，對應 Limiter 容量要依攻擊流量設計。Redis 或控制面失敗時的處理見 Failure Handling、Observability 與面試追問。

Failure Handling、Observability 與面試追問

1. Failure policy 依 endpoint 風險選擇

Redis、config service 或 quota control plane 失敗時，高風險、付費或易 abuse endpoint 採 fail closed；低風險讀取可短暫 fail open；也可退回保守的 local static limit。偵測方式是 Redis 呼叫設 5–10ms timeout 加 circuit breaker：滑動時間窗內錯誤率超過門檻就切到本地 1/N 額度，進入 half-open 後放少量請求探測 Redis 是否恢復。

2. Client contract 必須避免 retry storm

超限回 429，附 Retry-After、remaining quota、limit 與 reset time，讓 client 使用 backoff 加 jitter，而非同步重試。

3. 觀測同時證明保護與公平

量測 allow／reject rate、decision latency、error rate、bucket remaining、quota lease、over-admission、config propagation、top rejected clients 與熱點 endpoint。每個 global 誤差都要可量化與可觀測。

Limiter 容量要依攻擊流量設計

請求要先判定才能拒絕，每個被拒絕的 request 同樣消耗查詢與網路成本。

  • 例：正常尖峰 2k QPS、攻擊 50k QPS 時，只依 2k 設計會先打垮 limiter 本身。
  • 所以 limiter 不能是唯一一層；大部分攻擊流量要在更前面、更便宜的層先被擋下，見 分層防禦，攻擊流量在哪一層被擋下？。

Every request must be checked before it can be rejected, so the limiter must be sized for attack traffic, not normal peak.

分層防禦，攻擊流量在哪一層被擋下？

越前面越便宜、越粗；越後面越精準、越貴。

層 看得到什麼 典型規則 角色
Edge／WAF（CDN 節點，origin 之前） IP、header、路徑、地理位置、bot 指紋 IP 信譽與黑名單、per-IP rate rule、geo block、JS challenge／CAPTCHA 吸收大部分攻擊流量；容量由供應商擴展，不消耗自家頻寬與 LB
Load balancer 連線 只負責分流 不是限流層
API gateway device、token、IP 網段 per-device、per-subnet Token Bucket 削掉 edge 漏下的分散流量
業務服務 + Redis 帳號、手機號、業務狀態 per-phone、per-account、驗證次數 精準規則，只處理已被削減的流量
昂貴下游之前 總量 全域預算 + circuit breaker 成本保險，不是第一道防線

Cheap, coarse checks at the edge absorb most of the attack; precise per-identity checks run deeper, on traffic that has already been reduced.

分層是分工，global cap 放在昂貴下游之前

1. Edge／WAF 看不到業務身分

它不知道手機號或帳號，所以「每個手機號 60 秒 1 次」仍要放在業務服務。分層是分工，不是重複檢查。

2. Global cap 的位置決定對錯

單一 global cap 放在最前面當主要防線，攻擊流量吃光額度後，合法請求跟著被拒，等於替攻擊者完成 DoS。放在昂貴下游之前當成本上限才是正確用法。

Edge／WAF：WAF 檢查內容，rate rule 檢查頻率

WAF（Web Application Firewall）是 origin 前的 L7 reverse proxy，依規則比對 method、path、header、query、body、IP 信譽、地理位置與 bot 訊號，動作有 allow、block、challenge（JS challenge／CAPTCHA）與 count（只記錄）。Rate limiting 只是其中一類規則。

延伸：Edge／WAF：依攻擊類型對應防禦手段、Edge／WAF：新規則先 count 再 block、Edge／WAF：Origin 只接受 edge 流量，規則變更也要灰度。

A WAF inspects what a request contains; rate limiting controls how often requests arrive. I put managed rules, bot challenges and per-IP rate rules at the edge, lock the origin to edge traffic only, and roll out new rules in count mode before blocking — the WAF reduces load and known attacks, but parameterized queries and per-identity limits still live in the application.

Edge／WAF：依攻擊類型對應防禦手段

攻擊 WAF 手段 限制與後端仍要做的事
注入類：SQL injection、XSS、path traversal、command injection Managed rule set（例如 OWASP Core Rule Set）比對 signature，並以 anomaly score 累計多條規則命中 只認得已知 pattern，編碼繞過仍可能漏；後端仍要 parameterized query、input validation 與 output encoding
已知漏洞利用，例如 Log4Shell 供應商發布 virtual patch 規則，先擋 exploit payload 爭取修補時間，不取代升級套件
Bot：credential stuffing、scraping、OTP 轟炸 Bot score、TLS 指紋（JA3／JA4）、IP 信譽、JS challenge／CAPTCHA 進階 bot 使用住宅 proxy 與真實瀏覽器；per-account、per-phone 規則仍在業務層，見 Login 與 OTP 的典型限流規則
L7 DDoS：HTTP flood Per-IP／per-path rate rule、流量異常自動偵測、對可疑來源發 challenge 大量 IP 低速分散攻擊時，每個 IP 都不超限，要靠 gateway 的 per-device、per-subnet 規則
L3／L4 volumetric：SYN flood、UDP amplification 不屬於 WAF 規則；由 CDN／scrubbing network 的 anycast 容量吸收 同一供應商常一起提供，但要確認合約涵蓋範圍

Edge／WAF：新規則先 count 再 block

新規則先以 count／log 模式觀察 false positive，確認後才切 block。對誤判集中的 path（例如檔案上傳、富文本 API）設範圍明確的例外，不要整條規則關掉。

觀測 per-rule hit、block rate、challenge 通過率，以及被擋請求中的已登入用戶比例。

Edge／WAF：Origin 只接受 edge 流量，規則變更也要灰度

1. Origin 必須只接受 edge 流量

攻擊者一旦找到 origin IP 就能繞過 WAF。Origin 防火牆只放行 CDN 的 IP 段，或以 mTLS、edge 注入的 secret header 驗證來源。

2. WAF 規則本身也會造成事故

WAF 在每個 request 的路徑上。2019 年 Cloudflare 一條 WAF regex 規則造成 backtracking，全球節點 CPU 耗盡。Regex 規則要測試最壞情況效能，並分批上線。

Login 與 OTP 先建立威脅模型

Public API 限流以公平與延遲為先；login 與 OTP 限流主要防濫用與成本。

  • 例如每封簡訊約 NT$1，攻擊 50k QPS 持續一分鐘就是 300 萬封、約 NT$300 萬，還可能讓簡訊商限速，真實用戶收不到 OTP。
  • 6 位數 OTP 只有 100 萬種組合，可被暴力猜中。

因此優先序是：防濫用與正確性 → 攻擊期間合法用戶仍可使用 → 延遲。

For login and OTP, the main threat is abuse and cost, not fairness. I rank abuse prevention first, availability for real users during an attack second, and latency third — and I fail closed when the limiter is unavailable.

Login 與 OTP 的典型限流規則

規則依身分精準限制，前提是先建立威脅模型：Login 與 OTP 先建立威脅模型。以下是示意，依產品調整：

  • OTP 發送：per phone 每 60 秒 1 次、每小時 5 次；另設 per IP、per device 上限。
  • OTP 驗證：每個 code 最多試 5 次，超過即作廢。
  • 登入失敗：per account 15 分鐘 5 次後要求 CAPTCHA 或 step-up 驗證；不直接鎖帳號，否則攻擊者可以故意鎖住受害者。

延伸：Login 與 OTP 的 key 數量與故障回應。

Login 與 OTP 的 key 數量與故障回應

1. Key 數量由攻擊者決定，不由 DAU 決定

隨機手機號會讓每個請求建立新 key，50k/s 持續一小時約 1.8 億個。用 TTL ≈ capacity ÷ refillRate 回收、在建立手機號 key 之前先以 IP／device 限流，並驗證號碼格式，控制記憶體。

2. 超限與 limiter 故障是兩件事

超限回 429；limiter 自身逾時或不可用屬於 failure，OTP 發送採 fail closed，回 503 加 Retry-After。
